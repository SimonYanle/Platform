- **按生命周期拆分，而非按内容拆分**：待办和记录的生命周期根本不同——待办会被完成、会失效、需要删除；记录一旦写下就是既成事实，不该动。把两者放同一个文件，必然二者取一：要么改写历史条目（违反 append-only），要么留一堆已失效的勾选框。今天的文件正好演示了后者：6 条遗留里有 4 条早已完成，却还挂在历史条目里，读的人得逐条去比对才知道哪些还有效。

- **本轮改写了历史条目**：删除历史条目里的「遗留与下一步」小节，直接违反了「不改写历史」这条硬性要求。这是格式迁移的一次性例外，不构成先例。


- 新建 PowerShell profile，写入 `[Console]::OutputEncoding` 与 `$OutputEncoding` 的 UTF-8 设置。

### 决策与权衡

- **「或」的真实取舍**：上一轮我论证「或」等于放宽、会让价值判据形同虚设，这个论证漏了一半。「或」的独有好处是能捕捉**纯讨论型回合**——没改一行代码但定下了方案，这种回合在「且」下会被类型判据直接挡掉，而它恰恰是判断密度最高的。今天关于触发方式的整轮讨论就属于这一类。
- **代价与缓解**：代价确实存在——类型符合但无判断含量的改动重新获得了记录资格，也就是此前被手动撕掉的那一类。缓解方式不是收紧判据，而是约束篇幅：这类记录只留「改动」小节。把「该不该记」和「该记多长」拆成两个问题，比用判据一刀切更贴合实际。
- **profile 写 BOM 而非纯 ASCII 注释**：PowerShell 5.1 按 ANSI 解码无 BOM 的 `.ps1`，中文注释会乱码。两个选项是「注释改英文」或「文件加 BOM」，选后者，因为项目其余文档全是中文，为一个文件破例会造成不一致。

### 验证

- profile 前三字节为 `EF BB BF`。
- 新开 PowerShell 进程（加载 profile）能正确输出中文注释，且 `[Console]::OutputEncoding.WebName` 返回 `utf-8`，确认设置在新会话中自动生效。

### 卡点与修复

- 现象：**预判**写入带中文注释的无 BOM `.ps1` 会被 PowerShell 读成乱码。写入时并未实测，属于预防性处理。
- 推断的根因：PS 5.1 对无 BOM 的 `.ps1` 按系统 ANSI 代码页解码。
- 解法：以 `UTF8Encoding($true)` 重写文件补上 BOM。
- 该推断已于 16:57 实测确认成立，但当时另附的一处归因是错的，见 16:57 条目。

### 决策与权衡

- **两道门取「且」而非「或」**：这是本轮唯一有实质分歧空间的选择。取「或」意味着任一满足即记录，而类型门本就宽松（任何改动都能被论证成「结构决策」），结果是价值门形同虚设、等于没改。取「且」则两道门互补：类型门挡琐碎改动，价值门挡为交作业而写的空记录。代价是「没有任何判断含量的小 Bug 修复」不会留下痕迹——接受，因为那种修复本身也不值得未来的人读。
- **保留类型门而非只留价值门**：价值门是主观判据，单独用会漂移。类型门提供一个客观的粗筛，先排掉明显不该记的，再让价值门做细筛。
- **不代做首次提交**：提交信息和时机属于用户决定的范围，仅暂存待命。

- 未在本仓库做拦截测试——上一轮已在临时仓库覆盖 4 个场景，此处重复测试需要制造一次失败提交，收益不足。

### 卡点与修复

- 现象：`[Console]::OutputEncoding = [Text.Encoding]::UTF8` 在下一次 shell 调用时又失效了。

## 14:56 · Devlog 触发方式定为 git pre-commit 兜底

```yaml
type: chore
scope: 协作规范 / git 钩子
status: done
files:
  - .githooks/pre-commit
  - AGENTS.md
  - .cursor/rules/devlog.mdc
```

### 改动

- devlog 目录从 `docs/devlog/` 移到根 `devlog/`，删除 `docs/`，同步 `AGENTS.md` 与 `devlog.mdc` 里的 5 处路径引用。
- 新增 `.githooks/pre-commit`：提交若含实质文件而当天 devlog 未一并 `git add` 则拦下；只改 `devlog/`、`AGENTS.md`、`.cursor/`、`.githooks/` 时不触发；可用 `--no-verify` 或 `SKIP_DEVLOG=1` 跳过。
- `AGENTS.md` 与 `devlog.mdc` 补上「触发方式」「写入时机」两节。

### 决策与权衡

- **选 pre-commit，否掉 Cursor `stop` 钩子**：两者都是强制关卡，区别在触发点。`stop` 卡在 agent 每轮结束，会给每一轮对话施加交作业压力，从而催生「今天改了 X 文件」这类为过关而写的空记录。pre-commit 卡在人主动提交的时刻，是天然的批次边界，压力性质完全不同。附带好处是它对人和 agent 一视同仁。
- **明确承认钩子的能力边界**：它只能验证记录存在，无法验证记录有价值，因此防漏记有效、防水记无效甚至轻微鼓励水记。所以把它定位成兜底网，内容质量仍由 `devlog.mdc` 的判定标准承担，并把这句话直接写进两份文档，防止以后误以为有钩子就够了。
- **已知弱点**：提交越稀疏，钩子越松——一次提交压着多个决策时，它只要求「有 devlog 改动」。暂不处理，先看实际提交频率。
- **钩子放 `.githooks/` 而非 `.git/hooks/`**：后者不进版本控制，重新 clone 即失效。代价是需要一次性 `git config core.hooksPath .githooks`，已写入 `AGENTS.md`。
- **写入时机定在「汇报之前」**：若先汇报再记录，devlog 会退化成汇报的复印件，对未来没有增量价值。

### 验证

- `sh -n .githooks/pre-commit` 语法检查通过。
- 在临时 git 仓库做了 4 个场景的端到端测试：仅 `app.js` 无 devlog → 拦下（exit 1，`git log` 中无该提交）；补当天 devlog → 通过；仅改 `AGENTS.md` → 通过且不要求 devlog；`--no-verify` → 通过。
- `date`/`grep`/`sed` 在 git 钩子环境中可用。此前从 PowerShell 直接调 `sh.exe` 报 `date: command not found` 是假警报，原因是那样调用不会带上 Git 的 `usr\bin` 路径。

### 心智转变

- 原以为所有强制机制都会催生形式主义记录，所以一并否掉了钩子方案。实际上关键变量不是「是否强制」而是「卡在哪个时间点」：卡在每轮结束会制造噪音，卡在提交边界则合理。

## 14:23 · 建立 AGENTS.md 与 Devlog 记录规范


### 改动

- 新建 `AGENTS.md`，作为对所有会话生效的协作约定，目前只有 Devlog 规则和沟通约定两节，项目状态一节留空待技术栈确定后补。

- 新建 `docs/devlog/_TEMPLATE.md` 作为条目模板，规则文件只引用它，不重复描述格式。
- 本条目即为规范的第一次实际应用。

### 决策与权衡

- **规则同时放 AGENTS.md 和 .cursor/rules/**：AGENTS.md 是人和 agent 都会读的入口，`.mdc` 是 Cursor 原生注入机制。只放前者会依赖模型主动读文件；只放后者则人翻仓库时看不到约定。代价是两处内容需要同步，因此把细节集中在 `.mdc`，AGENTS.md 只留摘要和指针。
- **按日期分文件而非单文件追加**：单个 `DEVLOG.md` 长期会膨胀到几千行，每次追加都要读整个文件。按天分文件让单次读写范围可控，也天然形成时间索引。代价是查历史要跨文件搜索，可接受。
- **触发条件定为「重要变更」而非「每次改动」**：每次改动都记录会产生大量「改了错别字」这类噪音，反而淹没真正的决策记录。因此在规则里同时给出「需要」和「不需要」两张清单，把判断标准写死，避免每次靠感觉。
- **格式选 YAML 元信息 + markdown 正文**：YAML 块承载可机器解析的字段（type/scope/status/files），markdown 承载叙述性内容。纯 markdown 不利于将来做统计或检索，纯 YAML 写不下决策叙述。
- **模板抽成独立文件**：规则文件按 Cursor 的建议要保持精简（50 行内），把完整模板塞进去会挤占篇幅。

### 验证

- 未做功能性验证——这四个文件都是纯文档，没有可执行逻辑。
- 已确认：文件均已写入磁盘，`.mdc` 的 frontmatter 含 `description` 与 `alwaysApply: true`，符合 Cursor 规则格式要求。
- 真正的验证要等下一次实际开发：观察 agent 是否会在重要变更后自动按此格式追加条目。
